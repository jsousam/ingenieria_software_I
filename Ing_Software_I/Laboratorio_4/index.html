Ingeniería de Software Aplicada I — Laboratorio N.º 4

Modelos de Desarrollo y Ciclos de Vida del Software

Del plano rígido a la construcción evolutiva: cómo decide un equipo de software por dónde empezar a construir

Autor: José Sousa Institución: Universidad Tecnológica de Panamá (Sede Panamá Oeste)

Todo sistema de software nace de una apuesta: ¿construimos el plano completo antes de levantar la primera pared, o levantamos la primera pared y ajustamos el plano sobre la marcha? Esa apuesta tiene nombre propio en la ingeniería de software, y se llama modelo de ciclo de vida.

1. El Paradigma Tradicional

El paradigma tradicional agrupa a los modelos de desarrollo más antiguos de la disciplina, aquellos que entienden el software como una obra de ingeniería civil: se planifica por completo antes de construir. Su representante más conocido es el modelo en cascada (waterfall), propuesto formalmente por Winston Royce en 1970, que organiza el trabajo en fases secuenciales — análisis de requisitos, diseño, implementación, verificación y mantenimiento — donde cada fase debe cerrarse por completo antes de abrir la siguiente.

La lógica detrás de este paradigma es la previsibilidad: si los requisitos están claros desde el inicio, documentar cada fase permite estimar costos, plazos y recursos con relativa exactitud, y deja un rastro de documentación útil para auditorías, contratos y proyectos regulados.

“Cada fase debe cerrarse por completo antes de abrir la siguiente: la promesa es previsibilidad a cambio de rigidez.”

2. Modelo Tradicional y sus Variantes

Puesto que la cascada pura resultó demasiado inflexible para proyectos reales — donde los requisitos casi nunca permanecen estáticos — surgieron variantes que conservan la estructura secuencial pero añaden mecanismos de retroalimentación:

• Cascada con retroalimentación: permite regresar a una fase anterior cuando se detectan errores, en lugar de avanzar en una sola dirección.

• Modelo en V: extiende la cascada emparejando cada fase de desarrollo con una fase de prueba correspondiente, reforzando la verificación temprana.

• Modelo por etapas ("Sashimi"): solapa ligeramente las fases para reducir los tiempos muertos entre ellas.

3. Modelo Incremental

El modelo incremental combina elementos del modelo en cascada con una idea distinta: en lugar de entregar el sistema completo al final, el producto se construye y se entrega en piezas funcionales llamadas incrementos. Cada incremento añade nuevas funcionalidades al sistema ya entregado, de modo que el cliente recibe software operativo desde etapas tempranas.

Esto reduce el riesgo de que un error de concepción se descubra solo hasta el final. Es especialmente útil cuando los requisitos generales están claros, pero se prevé que evolucionen con el uso real.

4. Modelo Iterativo

El modelo iterativo propone construir el software mediante ciclos repetidos (iteraciones), donde en cada vuelta se revisan y refinan los requisitos, el diseño y la implementación de una versión anterior. A diferencia del incremental, que suma piezas nuevas, el iterativo perfecciona lo que ya existe: cada iteración produce una versión más completa y más precisa del sistema.

Este modelo asume, desde el principio, que no es posible conocer todos los requisitos de antemano. Es la base conceptual detrás de buena parte de las metodologías ágiles modernas.

5. Modelo Espiral

Propuesto por Barry Boehm en 1986, el modelo espiral combina el enfoque iterativo con un componente que lo distingue de todos los anteriores: el análisis explícito de riesgos en cada ciclo. El proyecto avanza en forma de espiral a través de cuatro cuadrantes que se repiten en cada vuelta:

1. Determinar objetivos, alternativas y restricciones.
2. Evaluar alternativas e identificar y resolver riesgos.
3. Desarrollar y verificar el producto de esa vuelta.
4. Planificar la siguiente iteración.

Cada vuelta de la espiral es más costosa y ambiciosa, lo que lo hace adecuado para proyectos grandes, costosos y de alto riesgo.

6. Modelo Orientado a la Reutilización

Este enfoque parte de la premisa de que no todo software debe construirse desde cero. Estructura el proceso en torno a la identificación, adaptación e integración de componentes ya existentes (bibliotecas, frameworks, servicios).

Sus etapas incluyen el análisis de componentes disponibles, la modificación de requisitos para ajustarse a lo disponible, el diseño del sistema alrededor de ellos y su integración final. Reduce tiempo y costo de desarrollo, pero exige cuidado en la compatibilidad y mantenimiento de dependencias.

Conclusión

Ningún modelo es universalmente superior: la elección depende de qué tan estables sean los requisitos, del tamaño y el riesgo del proyecto, y de cuánto margen exista para aprender sobre la marcha. Comprender estas alternativas permite a un equipo de ingeniería elegir el camino más adecuado para construir un sistema.

Resumen Sintético: En una Mirada

Modelo Idea Central Mejor cuando
Tradicional / Cascada Fases secuenciales y documentadas Requisitos estables y claros
Incremental Se entregan piezas funcionales El cliente necesita valor temprano
Iterativo Se refina lo ya construido El problema se entiende poco a poco
Espiral Iteración + análisis de riesgo Proyecto grande y de alto riesgo
