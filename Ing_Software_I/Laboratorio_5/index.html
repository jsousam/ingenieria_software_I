1. Entorno de desarrollo del software

Introducción

El entorno de desarrollo es todo el contexto en el que nace un sistema: la organización que lo necesita, las personas que lo usarán, los procesos que apoyará, las herramientas y metodologías del equipo, y las restricciones de tiempo, costo y tecnología. Un software no existe aislado: se inserta en un negocio y debe hacerlo mejor de lo que ya funciona.

Personas

Clientes, usuarios, analistas, desarrolladores, testers y gerentes.

Procesos

Metodología (cascada, RUP, Scrum), gestión de requisitos, control de cambios.

Herramientas

IDE, control de versiones, gestión de proyectos, modelado UML, pruebas.

Organización

Reglas, políticas, cultura, sistemas existentes y presupuesto.
Idea clave: la mayoría de los fracasos de software no se deben al código, sino a no haber entendido bien el negocio que el sistema debía apoyar.

Entendimiento del negocio

Antes de definir requisitos hay que responder: ¿qué hace la organización, para quién, cómo y con qué reglas? Entender el negocio permite que los desarrolladores y los expertos del dominio hablen un mismo idioma.

  • Identificar el propósito y la visión: misión, metas y clientes.
  • Reconocer a los interesados (stakeholders): quién decide, quién opera y quién se ve afectado.
  • Levantar procesos actuales: qué actividades ocurren, quién las hace y con qué información.
  • Documentar reglas del negocio: políticas y restricciones (por ejemplo, "no se vende sin existencia").
  • Definir un glosario: un vocabulario común evita ambigüedades.

Para lograrlo se usan las técnicas de recopilación de información: entrevistas, cuestionarios, observación directa, revisión de documentos, talleres (JAD) y prototipos.

Mejoramiento del proceso actual

Automatizar un proceso malo solo produce errores más rápido. Por eso, antes de construir el sistema se analiza el proceso actual para mejorarlo (Business Process Improvement).

1. Documentar el proceso actual➜2. Detectar problemas➜3. Rediseñar➜4. Implementar➜5. Medir y ajustar

Buena práctica: definir indicadores antes y después (tiempo por trámite, errores por mes, costo) para demostrar que el cambio realmente mejoró algo.

2. El modelo del negocio

Un modelo del negocio es una representación simplificada de cómo funciona una organización. Su propósito es que todos los involucrados compartan una misma comprensión del negocio y que de él se deriven los requisitos del sistema. En el Proceso Unificado (RUP) es la disciplina de Modelado del Negocio, y se apoya en UML.

ModeloPregunta que respondeHerramienta UML
Dominio¿Qué conceptos existen y cómo se relacionan?Diagrama de clases conceptual
Casos de uso del negocio¿Qué procesos ofrece el negocio y a quién?Diagrama de casos de uso
Objetos del negocio¿Quién colabora y con qué para realizar cada proceso?Diagramas de actividad, secuencia y clases

2.1 Modelo del dominio

Describe los conceptos del mundo real (entidades) relevantes para el negocio, sus atributos y sus relaciones, sin pensar en tecnología ni en cómo se guardarán los datos. Es un "diccionario visual" del negocio.

  • Clases conceptuales: Cliente, Producto, Factura, Proveedor.
  • Atributos: nombre, código, fecha, precio.
  • Asociaciones y multiplicidad: un Cliente realiza 0..* Pedidos; un Pedido contiene 1..* Productos.
  • Reglas de negocio: restricciones que las relaciones deben cumplir.

Se construye identificando sustantivos en las descripciones del negocio y filtrando los que no aportan (sinónimos, atributos disfrazados, conceptos fuera de alcance).

2.2 Modelo de casos de uso del negocio

Muestra los procesos del negocio desde el punto de vista de quienes se benefician de ellos. No describe el sistema informático, sino la organización.

  • Actor del negocio: alguien externo que interactúa con la organización (cliente, proveedor, ente regulador).
  • Caso de uso del negocio: un proceso que entrega un resultado de valor a un actor (por ejemplo, "Vender producto").
  • Trabajador del negocio: rol interno que ejecuta el proceso (cajero, bodeguero); no es un actor externo.
Diferencia clave: un caso de uso del negocio describe qué hace la empresa para el cliente; un caso de uso del sistema describe cómo el software apoya a un usuario. Lo primero antecede y origina a lo segundo.

Cada caso de uso se documenta con una especificación: nombre, actores, objetivo, flujo normal, flujos alternativos y reglas del negocio.

2.3 Modelo de objetos del negocio

Explica cómo se realiza internamente cada caso de uso del negocio: qué roles y qué elementos participan y cómo colaboran.

Trabajador del negocio

Rol humano que actúa en el proceso. Ej.: Vendedor, Bodeguero.

Entidad del negocio

Información que se usa y persiste. Ej.: Factura, Inventario.

Unidad de trabajo

Conjunto de entidades que forman un todo. Ej.: Expediente del cliente.

Se representa con diagramas de actividad (flujo con carriles por responsable), diagramas de secuencia/colaboración y diagramas de clases del negocio.

2.4 Representación de un modelo de negocio: ejemplos prácticos

Ejemplo: tienda de repuestos con venta en mostrador y pedidos a proveedores.

ElementoEjemplo
Actores del negocioCliente, Proveedor
Casos de uso del negocioVender repuesto · Reponer inventario · Atender garantía
Trabajadores del negocioVendedor, Cajero, Encargado de bodega
Entidades del negocioRepuesto, Factura, Orden de compra, Existencia
Reglas del negocioNo se factura sin existencia · Toda compra mayor a un monto requiere aprobación

Flujo del caso "Vender repuesto":

  1. El Cliente solicita un repuesto al Vendedor.
  2. El Vendedor consulta la existencia con el Encargado de bodega.
  3. Si hay existencia, el Vendedor genera la cotización; si no, ofrece alternativa o pedido especial.
  4. El Cliente acepta y el Cajero emite la factura y cobra.
  5. El Encargado de bodega entrega el repuesto y actualiza el inventario.

Con este flujo se descubren mejoras: la consulta de existencia por llamada es lenta y sujeta a error, lo que sugiere un punto donde un sistema aportaría valor.

Otros ejemplos para practicar: matrícula en una universidad, préstamo en una biblioteca, cita en una clínica, pedido en un restaurante.

2.5 Pasando del modelo del negocio al modelo del sistema

El modelo del negocio es la base para definir qué debe hacer el software. Se identifican las actividades del negocio que conviene automatizar y se traducen a requisitos.

Modelo del negocioSe convierte en (modelo del sistema)
Trabajador del negocioActor del sistema (usuario con un rol)
Actividad o caso de uso del negocio automatizableCaso de uso del sistema / requisito funcional
Entidad del negocioClase de entidad del sistema y tabla de datos
Regla del negocioRegla de validación / requisito no funcional
Modelo del dominioBase del diagrama de clases y del modelo de datos
Negocio➜Procesos a automatizar➜Requisitos➜Casos de uso del sistema➜Diseño

Ejemplo: del proceso "Vender repuesto" surgen los casos de uso del sistema Consultar existencia, Generar cotización y Emitir factura, con actores Vendedor y Cajero, y clases como Repuesto, Factura y Existencia.

Conclusiones

  • Comprender el entorno y el negocio es el primer paso para construir software útil; sin él, los requisitos nacen incompletos.
  • Mejorar el proceso antes de automatizarlo evita digitalizar ineficiencias.
  • Los modelos de dominio, casos de uso y objetos del negocio se complementan: el primero define los conceptos, el segundo los procesos y el tercero quién los ejecuta.
  • La transición al modelo del sistema es trazable: cada requisito debe poder rastrearse hasta una necesidad real del negocio.
